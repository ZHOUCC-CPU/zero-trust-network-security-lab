# V0.9 Reproducibility and Release Checklist

**Project:** Zero Trust Network Security Lab
**Status:** Local V0.9 validation passed (25 October 2026)
**Baseline:** V0.8 Git commit `cb7c124`
**Runtime:** Windows 11 / WSL2 Ubuntu 24.04

## 1. Research scope

This project demonstrates controlled Linux network
microsegmentation using namespaces, veth, IPv4 routing,
and nftables forwarding policies.

It is not a complete enterprise Zero Trust Architecture.

The following are outside the demonstrated scope:
identity-based authentication, device posture assessment,
continuous authorization, and production deployment.

## 2. Environment prerequisites

Reference environment observed on 25 October 2026:

- WSL2 Ubuntu 24.04
- Linux kernel 6.6.87.2-microsoft-standard-WSL2
- Python 3.12.3
- iproute2 6.1.0
- nftables 1.0.9
- iperf3, ping, timeout, flock and sha256sum available

Other versions require separate compatibility verification.

## 3. Offline verification

Run from the repository root in WSL Ubuntu.

Check the revision and local changes:

```bash
git log -1 --oneline
git status --short
```

Run the V0.9 resource-checker self-test:

```bash
python3 -B scripts/v09_resource_integrity.py --self-test
```

Run the ten offline regression tests:

```bash
python3 -B tests/test_v09_resource_integrity.py
```

Validate the archived V0.8 experiment evidence:

```bash
python3 -B scripts/v08_evidence_validator.py   --session evidence/v08_runs/audit_20261024T155756056355Z_384   --plan tests/v08_audit_plan.json
```

The archived V0.8 run previously achieved 18/18 passing
scenarios. Revalidating its files does not constitute a new
live experiment.

Record actual command outputs and exit codes.

## 4. Read-only live environment inspection

Before running the V0.9 resource integrity checker:

- Confirm this is an authorized WSL test environment.
- Confirm no deployment or cleanup operation is running.
- Verify the project lock exists and is safely owned.
- If WSL restart removed the lock, initialize it only
  through a separately reviewed safe procedure.
- Ensure that sudo credentials are available.

Example:

```bash
sudo -v
python3 -B scripts/v09_resource_integrity.py --check
```

Expected clean-environment indicators:

- `PROJECT_NAMESPACES=NONE`
- `SUSPECT_HOST_INTERFACES=NONE`
- `PROJECT_STATE_PRESENT=NO`
- `V09_RESOURCE_INTEGRITY=PASS`

Unexpected resources or privilege failures must not
be interpreted as a successful clean-environment check.

The verifier is observational and must not delete resources.

## 5. Privileged experiment reproduction

A fresh live end-to-end reproduction is a separate,
explicitly authorized operation.

Before attempting one:

- Review architecture/DEPLOYMENT_SAFETY.md.
- Verify the topology and policy scripts and their hashes.
- Stage reviewed privileged files on a root-owned native
  Linux filesystem, not directly on /mnt/d.
- Confirm namespace names and expected host interfaces
  are unused.
- Acquire the project's existing coordination lock through
  the reviewed lifecycle scripts.
- Preserve previous experimental evidence.
- Use a new evidence session rather than overwriting
  archived V0.8 results.
- Capture deployment, policy, behavior, counter and
  teardown evidence.
- Validate cleanup and inspect the state file.
- Stop for manual review if ownership cannot be proved.

Do not rerun V0.8 --execute --commit as a generic
reproduction command: it is a release-specific workflow
with existing output and Git commit expectations.

No destructive failure injection is authorized by
this checklist.

## 6. Evidence acceptance

For each new live audit session, require:

- A recorded experiment plan and environment.
- Explicit expected behavior for each scenario.
- Actual network behavior and return status.
- Before/after nftables counter snapshots.
- Counter-delta checks tied to the expected rule.
- JSON and CSV records with consistent scenarios.
- SHA-256 provenance for retained evidence.
- Independent evidence validation.
- Verified normal cleanup and reported exceptions.

Separate simulated tests from live observations.

## 8. Known limitations

- Six representative access scenarios are not exhaustive.
- V0.7 performance measurements are environment-specific.
- Resource measurements include WSL guest-wide effects.
- Normal cleanup success does not prove complete
  recovery from arbitrary crashes or forced termination.
- Offline negative tests do not prove live fault tolerance.
- A clean project-specific resource check does not
  certify the entire host network configuration.
