# V1.0 Runtime Decision and Reproducibility

**Project:** Zero Trust Network Security Lab

**Version:** V1.0 research documentation

**Source baseline:** `fb6bbd0` (V0.9 local release)

**Status:** Locally accepted release candidate; V1.0 not yet published.

## 1. Purpose

This document explains the experimental runtime
decision, the evidence supporting that decision,
the safety boundaries, and the limits of
reproducibility.

It is based on the existing V0.2–V0.9 records.

No new experiment or cross-runtime comparison
is claimed here.

## 2. Selected runtime

The demonstrated environment uses:

- Windows 11 host.
- WSL2 Ubuntu 24.04.
- Four Linux network namespaces.
- Three veth pairs.
- Linux IPv4 routing.
- nftables gateway forwarding policy.
- Bash and Python test utilities.

The original V0.2 feasibility record reported
a WSL2 memory limit of 3 GB and an allocation
of four CPUs.

These are historical reported settings.
They must not be interpreted as measurements
of every later experimental session.

Source:
[V0.2 Runtime Validation](../evidence/V0.2_RUNTIME_VALIDATION.md).

## 3. Reason for selecting WSL2

The project aimed to evaluate network
microsegmentation on a personal computer
with limited available resources.

Linux namespaces share one kernel and avoid
requiring four separate virtual machines.

The selected WSL2 runtime supported the
observed deployment, routing, policy
enforcement, and experimental workflow.

This is a practical decision for the tested
laboratory environment.

It is not evidence that WSL2 is generally
more secure, efficient, or isolated than
a dedicated Linux virtual machine.

## 4. Implemented network structure

The experiment uses four namespaces:

| Namespace | Research responsibility |
|---|---|
| `employee-ns` | Simulated client zone |
| `app-ns` | Application service test zone |
| `data-ns` | Sensitive-data service test zone |
| `zt-gw-ns` | Routing and forwarding policy |

Three point-to-point IPv4 networks connect
the zones to the gateway:

| Zone link | Subnet |
|---|---|
| Employee to Gateway | `10.200.10.0/30` |
| Application to Gateway | `10.200.20.0/30` |
| Data to Gateway | `10.200.30.0/30` |

The gateway endpoint uses `.1` and each
corresponding zone endpoint uses `.2`.

The enforced nftables policy permits
Employee-to-Application TCP 8080 and
Application-to-Data TCP 5432.

Other tested new cross-zone flows are
denied by the forwarding policy.
Established and related return traffic
is handled through connection tracking.

The experiment principally evaluates
the gateway `forward` hook, not a
complete host or workload firewall.

Source:
[Architecture Design](../architecture/ARCHITECTURE_DESIGN.md).

## 5. Host boundary and privileged execution

The repository is stored on a Windows-mounted
DrvFS path.

Privileged deployment scripts must not be
executed directly from that mutable location.

The established experimental workflow uses
a separately reviewed, Ubuntu-native,
root-controlled staging directory.

Before privileged execution, the operator
must review and verify:

- The exact staged script and policy hashes.
- Root ownership and restrictive permissions.
- Project namespace and state identities.
- The shared operation lock.
- The expected project resource inventory.

Root-staged cleanup files must not be
overwritten merely because their formatting
differs from a repository copy.

During deployment, the project temporarily
creates named veth endpoints in the default
Linux network namespace before relocating
them into project namespaces.

Therefore, zero interaction with the default
Linux network namespace is not claimed.

No persistent host-wide firewall policy,
NAT configuration, or external route is
intentionally installed by this experiment.

The experiment does not authorize changes
to the Windows host firewall or network.

Source:
[Deployment Safety](../architecture/DEPLOYMENT_SAFETY.md).

## 6. Experimental reproducibility

The recorded versions provide distinct forms
of verification:

| Version | Evidence role |
|---|---|
| V0.3 | Namespace topology and normal cleanup |
| V0.4 | Default-deny forwarding behavior |
| V0.5 | Repeated regression evidence |
| V0.6 | Baseline-versus-segmented comparison |
| V0.7 | Bounded performance measurements |
| V0.8 | Individual-scenario firewall counter audit |
| V0.9 | End-to-end trial and normal cleanup |

V0.8 retained before-and-after counter
snapshots around individual scenarios.

V0.9 retained before-and-after snapshots
around each complete six-scenario round.

The V0.9 trial completed 18/18 expected
network scenarios and 3/3 round-level
counter comparisons.

Its 15 primary evidence files passed
SHA-256 consistency validation.

These results apply to the recorded sessions.
They are not proof of universal
cross-host reproducibility.

## 7. Safe reproduction boundaries

Offline documentation and evidence review
should be preferred when a live experiment
is not required.

A new live run would require a separately
authorized privileged execution phase,
including preflight identity verification,
staged script validation, shared locking,
and explicit cleanup requirements.

Normal teardown must verify that expected
project namespaces, suspicious residual
interfaces, and project state are absent.

On an inconsistent ownership marker,
unknown namespace identity, unexpected
resource, or unsafe cleanup condition,
automatic deletion must stop.

Do not delete unrelated resources to
force a successful verification result.

The project lock under `/run/lock` may
disappear across WSL restarts. A missing
lock requires separately reviewed
initialization rather than bypassing
synchronization checks.

The V0.9 checklist documents the
historical release validation workflow.

Source:
[V0.9 Reproducibility Checklist](V0.9_REPRODUCIBILITY_CHECKLIST.md).

## 8. Alternative VM runtime

The original proposal included an Ubuntu
Server virtual machine as an alternative
experimental environment.

However, the available research release
evidence does not establish a completed,
equivalent Ubuntu Server VM comparison.

Accordingly, no comparative VM latency,
throughput, memory, privilege isolation,
or security superiority result is claimed.

Any future comparison would need
equivalent topology, policy, tools,
test inputs, sampling, and cleanup checks.

This limitation leaves the original
cross-runtime research question
partially unanswered.

## 9. Evidence and security limitations

The experiment does not demonstrate:

- Authenticated user or workload identities.
- Device posture or continuous authorization.
- Comprehensive IPv6 enforcement.
- Complete spoofing and bypass resistance.
- Production application security.
- Exhaustive cross-zone traffic coverage.
- Recovery from every abnormal interruption.
- Independent evidence authentication.
- Production Zero Trust certification.

V0.7 performance findings are descriptive.
The measurements do not demonstrate
statistically established firewall overhead
or maximum network capacity.

SHA-256 checking supports consistency
between archived files and recorded hashes.
It is not a signed, independently
authenticated provenance guarantee.

## 10. V1.0 research-release interpretation

WSL2 Ubuntu was a workable runtime for the
demonstrated lightweight microsegmentation
experiments.

The measured results support conclusions
about the tested topology, forwarding
policy, audit methodology, and normal
operational lifecycle.

The complete Ubuntu Server VM comparison
and production deployment claims remain
outside the validated evidence.

This document is part of the V1.0
documentation phase.

It does not execute a network trial,
install a VM image, modify host routing
or firewalls, perform attack activity,
or create a Git commit.

See the
[V1.0 Research Report](../reports/V1.0_RESEARCH_REPORT.md)
for the integrated scientific discussion.
