# Zero Trust Network Security Lab

## Research Portfolio Summary — V1.0 Release Candidate

**Research focus:** Network microsegmentation,
least-privilege access control, Linux network isolation,
and security verification.

**Technologies:** Windows 11, WSL2 Ubuntu 24.04,
Linux network namespaces, veth, nftables, Bash,
Python, JSON, CSV, and SHA-256.

**Status:** V0.9 locally validated and committed.
V1.0 research documentation has passed local acceptance and is pending publication.

## Project Overview

The Zero Trust Network Security Lab is an experimental
network security project investigating how lightweight
Linux isolation and stateful firewall policies can
support repeatable microsegmentation testing.

The project models three network zones connected
through a dedicated policy enforcement gateway.
It uses four Linux network namespaces, three
virtual Ethernet links, internal IPv4 routing,
and a default-deny nftables forwarding policy.

The implementation focuses on explicit network
access control, experimental verification,
auditable evidence, and safe resource cleanup.

It demonstrates network microsegmentation inspired
by Zero Trust principles rather than a complete
production Zero Trust Architecture.

## Research Objectives

The project investigates whether:

1. A resource-constrained Linux environment can
   support repeatable network segmentation.
2. A default-deny forwarding policy can preserve
   approved connections while denying specified
   unauthorized cross-zone traffic.
3. The experimental policy and gateway have
   measurable operational and performance costs.
4. The chosen WSL2 runtime has documented
   capabilities and limitations relative to
   alternative virtualization environments.

The fourth objective remains only partially
addressed because an equivalent Ubuntu Server
VM comparison has not been completed.

## Technical Architecture

The implemented topology consists of:

| Network namespace | Role |
|---|---|
| `employee-ns` | Simulated employee/client zone |
| `app-ns` | Simulated application service zone |
| `data-ns` | Simulated sensitive-data service zone |
| `zt-gw-ns` | Isolated forwarding policy gateway |

Three point-to-point IPv4 networks connect
the zones to the gateway:

- Employee: `10.200.10.0/30`
- Application: `10.200.20.0/30`
- Data: `10.200.30.0/30`

The gateway policy explicitly permits:

- Employee to Application: TCP 8080.
- Application to Data: TCP 5432.
- Established and related return traffic.

Other tested new cross-zone connections are
denied by the gateway forwarding policy.

TCP 5432 is represented by a temporary test
server, not a production PostgreSQL database.

## Key Experimental Findings

### Controlled access-control comparison

In V0.6, the project compared three permissive
baseline rounds against three segmented rounds.

All 36 scenario executions matched their
condition-specific expectations.

The segmented condition produced:

- 12/12 expected unauthorized-connection denials.
- 6/6 expected authorized-connection successes.
- Zero observed false allows or false denies
  within the defined six-scenario test matrix.

The permissive baseline intentionally allowed
the disallowed-under-segmentation flows.
Those observations were expected control results.

### Firewall security auditing

V0.8 completed 18/18 expected network scenarios
and retained before-and-after nftables rule
counter snapshots for individual scenarios.

A separate V0.9 trial completed 18/18 expected
scenario executions and three successful
round-level counter comparisons.

The V0.9 experiment also recorded successful
normal topology cleanup and a passing
post-cleanup resource integrity check.

The primary 15 V0.9 evidence files passed
local SHA-256 consistency verification.

### Performance observations

V0.7 measured bounded TCP connection timing
and receiver throughput for two permitted paths.

Observed median TCP connection timings were:

| Path | Baseline | Segmented |
|---|---:|---:|
| Employee to Application | 0.40397 ms | 0.41528 ms |
| Application to Data | 0.38466 ms | 0.41259 ms |

These small observed differences do not
establish statistically significant overhead
or production network performance.

## Engineering and Research Practices

The project incorporates:

- Least-privilege, default-deny forwarding rules.
- Repeatable positive and negative connectivity tests.
- Baseline-versus-segmented experimental comparison.
- Structured JSON and CSV evidence.
- nftables packet-counter audit snapshots.
- SHA-256 evidence integrity checks.
- Root-controlled reviewed-script staging.
- Namespace identity and lifecycle verification.
- Protected cleanup and post-cleanup checks.
- Versioned research reports and evidence references.

## Security and Research Limitations

The current implementation does not provide
authenticated user or workload identity,
device posture assessment, continuous trust
evaluation, enterprise policy orchestration,
or comprehensive production security monitoring.

The principal firewall enforcement point is
the gateway IPv4 forwarding hook.

IPv6, source spoofing, local-input/output policy,
and other bypass conditions require further work.

Normal cleanup success does not prove complete
recovery from abnormal interruption or system crashes.

The experiments were conducted in a controlled
WSL2 environment. Equivalent testing against
an Ubuntu Server VM has not been established.

The experiments support claims about the tested
network policy and laboratory methodology,
not production deployment readiness.

## Research and Portfolio Value

This project demonstrates practical experience in
Linux network isolation, security policy design,
experimental methodology, test automation,
evidence validation, and responsible reporting
of technical limitations.

It can support discussion of network security
engineering, system security experimentation,
and reproducible research methods in an
academic or cybersecurity portfolio context.
