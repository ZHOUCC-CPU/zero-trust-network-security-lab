# V0.8 - Security Audit and Reproducibility Design

## 1. Objective

Validate segmented access-control decisions using
isolated network tests and nftables counter deltas.
Review reproducibility and evidence integrity.

This is a bounded security audit experiment,
not a production security monitoring system.

## 2. Experimental Scope

- Environment: WSL2 Ubuntu 24.04.
- Network: four isolated Linux namespaces.
- Gateway: zt-gw-ns.
- Policy: inet ztlab_v04, forward chain.
- Conditions: segmented policy only.
- Repetitions: three rounds.
- Cases per round: six.
- Planned scenario executions: 18.

## 4. Measurement Procedure

1. Validate ownership and identity of the deployed topology.
2. Verify the expected segmented nftables rules.
3. Capture the relevant counter before each scenario.
4. Execute one bounded isolated test scenario.
5. Capture the same counter after the scenario.
6. Calculate the non-negative packet-counter delta.
7. Check observed behavior against the expected verdict.
8. Check that the expected counter increased.
9. Save command outcomes, timestamps, and snapshots.
10. Verify evidence and perform guarded cleanup.

## 5. Evidence Schema

Each scenario record should include:

- scenario_id, round, source_namespace
- destination_ip, protocol, destination_port
- expected_verdict, observed_behavior
- expected_counter, packets_before, packets_after
- packet_delta, test_status, error_reason
- timestamp_utc and evidence file references

Evidence outputs should include JSON, CSV,
source log SHA-256 hashes, and a final report.

## 6. Safety Controls

- Never modify Windows or host-wide firewall rules.
- Never generate external network traffic.
- Never reset existing nftables counters.
- Do not enable persistent kernel logging.
- Validate namespace identity before privileged actions.
- Use reviewed root-owned scripts for live execution.
- Avoid concurrent scenarios during counter measurement.
- Refuse unknown resources instead of blindly deleting them.
- Keep tests time-bounded and verify final cleanup.

## 7. Interpretation and Limitations

- Counters describe aggregate packets, not individual events.
- A counter increase does not establish user identity.
- ALLOW requires a successful application-level check.
- DENY requires a verified blocked connection or probe.
- Counter deltas alone cannot prove the complete verdict.
- Shared drop counters cannot identify a specific flow.
- Concurrent traffic can affect measured counter deltas.
- Three rounds do not establish production reliability.

## 8. Acceptance Criteria

- All 18 planned scenario executions are accounted for.
- Every verdict is supported by behavioral observations.
- Expected rule-counter deltas are positive.
- JSON and CSV data agree with source evidence.
- Hash validation completes successfully.
- The isolated topology is safely cleaned up.
- The report states uncertainty and limitations.
