# V0.7 Performance Benchmark Design

## 1. Objective

Measure performance and resource differences between
the V0.3 baseline network and V0.4 segmented network.

This is a controlled WSL2 experiment, not a production
network-performance evaluation.

## 2. Experimental Conditions

- Baseline: V0.3 topology without lab nftables rules.
- Segmented: Same topology with V0.4 default-drop policy.
- Three repeated rounds per condition.
- Sequential order: Baseline, then Segmented.
- Identical test configuration for both conditions.

## 3. Authorized Network Flows

1. Employee to Application: TCP 8080.
2. Application to Data: TCP 5432.

Both flows are allowed under the V0.4 policy.

## 4. Performance Measurements

### TCP Connection Latency

- 30 connection probes per flow per round.
- Record mean, median, P95, and connection failures.
- TCP connection latency is not ICMP ping RTT.

### TCP Throughput

- Tool: iperf3.
- Duration: 5 seconds.
- Parallel streams: 1.
- Target bitrate: 50 Mbit/s.
- Record actual send/receive bitrate and retransmits.
- The target bitrate does not measure maximum capacity.

### CPU and Memory

- Read Linux /proc/stat and /proc/meminfo.
- Collect CPU usage and memory observations.
- Report WSL guest-wide metrics, not isolated nftables costs.

### Operational Overhead

- Measure topology deployment duration.
- Measure topology cleanup duration.
- Record the total evidence file size.

## 5. Service Lifecycle

- Start temporary listeners for latency tests.
- Stop these listeners before throughput tests.
- Start iperf3 servers for throughput measurements.
- Prefer one-off iperf3 server sessions.
- Use bounded timeouts and clean up child processes.
- Avoid simultaneous HTTP and iperf3 listeners
  on the same destination port.

## 6. Security Controls

- Run orchestration as the normal WSL user.
- Use reviewed root-owned scripts for privileged actions.
- Verify script ownership, permissions, and SHA-256.
- Do not run Windows-writable scripts directly as root.
- Check namespace ownership before cleanup.
- Reject unexpected existing namespaces or state files.
- Avoid modifications to the WSL host firewall.
- Do not configure NAT or external network traffic.
- Preserve diagnostic evidence after failures.

## 7. Evidence and Validation

- Create unique evidence directories.
- Save raw logs, JSON, and CSV.
- Record SHA-256 hashes.
- Validate measurement counts and data types.
- Preserve incomplete or failed tests as failures.
- Generate a final experimental report.

## 8. Limitations

- Results depend on WSL2 scheduling and host workload.
- Baseline and Segmented runs are not randomized.
- Fixed-rate tests do not establish maximum throughput.
- System-wide CPU and memory include unrelated activity.
- The experiment is limited to two authorized flows.
- Performance differences may have confounding factors.
