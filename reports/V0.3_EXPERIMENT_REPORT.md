# V0.3 Experimental Report
## Zero Trust Network Security Lab

### 1. Objective

The objective of V0.3 was to build and validate a lightweight, isolated network segmentation topology using Linux Network Namespaces, virtual Ethernet (veth) interfaces, and static routing.

This stage focused on network topology and connectivity. Formal Zero Trust access-control enforcement was not implemented.

### 2. Experimental Environment

- Platform: Windows 11 with WSL2
- Linux distribution: Ubuntu 24.04
- Configured WSL2 memory limit: 3 GB
- Configured WSL2 CPU limit: 4 logical processors
- Technologies: Linux Network Namespaces, veth, iproute2, shell scripting
- Network architecture: Three network zones connected through a dedicated gateway namespace

### 3. Network Topology

Four namespaces were deployed:

| Namespace | Role | IPv4 address |
|---|---|---|
| `employee-ns` | Employee zone | `10.200.10.2/30` |
| `app-ns` | Application zone | `10.200.20.2/30` |
| `data-ns` | Data zone | `10.200.30.2/30` |
| `zt-gw-ns` | Routing gateway | `10.200.10.1/30`, `10.200.20.1/30`, `10.200.30.1/30` |

Three veth pairs connected the business zones to the gateway. Static routes enabled communication between the three subnets. IPv4 forwarding was enabled inside `zt-gw-ns` only.

No NAT, external egress route, or formal firewall policy was configured by the V0.3 scripts.

### 4. Experimental Procedure

1. Staged reviewed Bash scripts in a root-owned directory inside the Ubuntu filesystem.
2. Deployed the four-namespace network topology.
3. Checked namespace existence, veth endpoints, IPv4 addresses, static routes, and gateway forwarding.
4. Verified connectivity between business zones and the gateway and between business zones using ICMP ping.
5. Updated the route-validation logic to normalize trailing whitespace after an initial false-negative check.
6. Recorded a successful topology validation log.
7. Ran the cleanup script with `--dry-run` to validate its planned actions and resource ownership checks.
8. Ran the normal cleanup procedure.
9. Independently inspected namespace names, project veth names in the default namespace, and the deployment state file for residual resources.

### 7. Limitations

V0.3 demonstrated topology construction, routing, connectivity, normal cleanup, and absence of the checked residual resources. It did **not** demonstrate a complete Zero Trust architecture or enforce default-deny network policies.

Specifically:

- No default-deny inter-zone nftables policy was implemented.
- No fine-grained allowlist or unauthorized-traffic blocking was evaluated.
- No user identity, workload identity, device posture, or continuous trust verification was implemented.
- No formal network throughput or latency benchmark was performed.
- Abnormal termination, deliberate fault injection, and partial-cleanup recovery were not fully exercised in the live environment.
- This report documents one successful normal deployment and cleanup cycle; long-term repeatability has not yet been established.

### 8. Next Stage: V0.4

V0.4 will evaluate controlled inter-zone network access using nftables within the isolated laboratory topology. Planned work includes default-deny forwarding, narrowly scoped allow rules, unauthorized-traffic denial, and regression tests with preserved evidence. These controls constitute network microsegmentation experiments rather than a complete Zero Trust implementation.

### 9. Conclusion

The V0.3 experiment successfully established and validated an isolated four-namespace network topology in WSL2 Ubuntu. All 36 topology checks passed after a route-checking whitespace issue was corrected. The normal cleanup completed successfully, and the subsequent checks found zero residual failures for the specified project resources.

This topology provides an experimental baseline for access-control enforcement and evaluation in V0.4.
