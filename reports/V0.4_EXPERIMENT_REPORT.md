# V0.4 Experimental Report: Stateful Network Microsegmentation with nftables

- **Project:** Zero Trust Network Security Lab
- **Stage:** V0.4 — Network Access Control and Regression Validation
- **Platform:** Windows 11 / WSL2 / Ubuntu 24.04
- **Experiment date:** 18 October 2026 (UTC)
**Result:** Six of six observed automated regression scenarios passed; the final cleanup check detected no residual failures among the specified resources.

## 1. Executive Summary

V0.4 extended the four-namespace network topology validated in V0.3 by installing a stateful `nftables` forwarding policy inside a dedicated gateway network namespace, `zt-gw-ns`. The policy was designed to deny inter-zone traffic by default while permitting two narrowly specified TCP flows: Employee to Application on port 8080 and Application to Data on port 5432.

The firewall was checked for syntax, installed in the isolated gateway, inspected in the live kernel ruleset, and exercised with real TCP and ICMP traffic. Six manually executed scenarios produced the expected outcomes, followed by six successful automated regression scenarios. Firewall counters supported the observed permit and deny decisions. The topology was subsequently cleaned up, and the independent final check reported zero failures across four namespace names, six specified interface names, and the deployment state file.

**Scope statement:** This is a demonstration of stateful Layer 3/4 network microsegmentation. It is **not** a complete Zero Trust implementation: no identity-aware authentication, device-posture evaluation, application-layer authorization, or continuous identity verification was demonstrated.

## 2. Objectives and Success Criteria

The objectives of V0.4 were to:

1. Apply a default-deny policy to **forwarded traffic** in the isolated gateway namespace.
2. Permit only the specified new TCP connections between selected zones.
3. Permit return packets belonging to established or related connections.
4. Verify both permitted and blocked traffic with live tests and kernel rule counters.
5. Repeat the six scenarios through an automated regression script.
6. Preserve experiment evidence and confirm normal cleanup of the lab topology.

Success for the tested access-control matrix required both allow scenarios and all four deny scenarios to match their expected results. This criterion was met in the observed run.

## 4. Security Policy and Enforcement Boundary

The firewall table `inet ztlab_v04` was installed **inside `zt-gw-ns`**, with a `forward` chain using `policy drop`. The rules were, in evaluation order:

| Order | Match / condition | Action | Rationale |
|---|---|---|---|
| 1 | `ct state established,related` | Accept and count | Allow return/related traffic for tracked connections |
| 2 | `gw-emp` to `gw-app`, source `10.200.10.2`, destination `10.200.20.2`, new TCP connection to port `8080` | Accept and count | Employee access to the Application test service |
| 3 | `gw-app` to `gw-data`, source `10.200.20.2`, destination `10.200.30.2`, new TCP connection to port `5432` | Accept and count | Application access to the Data test service |
| 4 | Any other forwarded traffic | Drop and count | Enforce default-deny behavior |

The corresponding firewall chain was configured with the equivalent of:

```nft
chain forward {
    type filter hook forward priority 0; policy drop;
    ct state established,related counter accept
    iifname "gw-emp" oifname "gw-app" ip saddr 10.200.10.2 ip daddr 10.200.20.2 tcp dport 8080 ct state new counter accept
    iifname "gw-app" oifname "gw-data" ip saddr 10.200.20.2 ip daddr 10.200.30.2 tcp dport 5432 ct state new counter accept
    counter drop
}
```

**Boundary:** The policy controls routed packets traversing the gateway's `forward` hook. It does not constitute a host-wide firewall, does not govern every possible namespace-local `input`/`output` path, and does not assert user or workload identity. The dedicated gateway namespace keeps this experiment's rules separate from the default Ubuntu network namespace.

The port `5432` test used a temporary **Python HTTP server bound to that TCP port**. It validated TCP connectivity through the policy; it did not test PostgreSQL or database authorization.

## 5. Deployment and Validation Method

The observed procedure was:

1. Confirm `nft` and Python were available and no prior project namespace remained.
2. Create the V0.4 policy file and validate it using `nft --check` inside a temporary, isolated network namespace.
3. Create the policy loader; check its Bash syntax and confirm the loader's state-field names matched the V0.3 deployment script (`OWNER`, `PHASE`, `NS_zt_gw_ns_INODE`).
4. Copy the reviewed policy and scripts into a root-controlled staging directory. Observed permissions included `600` for the policy and `700` for executable scripts.
5. Re-deploy the V0.3 topology and confirm the 36-check pre-policy baseline.
6. Load V0.4 into `zt-gw-ns`, then read back the live nftables table, chain, rule order, and counters.
7. Execute manual allow and deny scenarios, observing service readiness, client outcome, and the relevant nftables counters.
8. Run the root-staged six-scenario regression script and save its terminal output.
9. Check for lingering namespace processes; perform cleanup dry-run, normal cleanup, and independent post-cleanup checks.

The policy loader reported:

```text
PASS: V0.4 firewall loaded into zt-gw-ns
POLICY_LOAD_EXIT_CODE=0
```

The live ruleset inspection completed with `RULESET_CHECK_EXIT_CODE=0` and displayed the intended `forward` chain with `policy drop`.

## 9. Limitations and Security Interpretation

- **Identity and trust:** Controls are based on interfaces, addresses, TCP ports, and connection state rather than authenticated user/workload identity or device health.
- **Enforcement scope:** Only routed traffic passing through the gateway's `forward` hook was evaluated. Traffic originating or terminating on a gateway interface, local zone policies, and other bypass paths were not fully assessed.
- **Policy breadth:** The regression matrix contains six representative scenarios. It does not exhaust all source/destination/protocol/port combinations, connection-state edge cases, packet fragmentation, or anti-spoofing tests.
- **Test services:** Temporary Python servers confirmed listener availability and TCP connectivity. There was no actual PostgreSQL service, application-layer access-control assessment, or production workload.
- **Performance:** No network throughput, packet-loss baseline under load, resource-consumption benchmark, or latency comparison was performed.
- **Recovery:** The observed normal deployment, policy load, and cleanup succeeded. Live fault injection, interruption during setup/cleanup, crash recovery, and repeated full-cycle soak testing were not documented as completed.
- **Attribution:** In deny tests, both client failure and matching nftables drop-counter increases support firewall enforcement. The results should not be generalized to untested attacks.

## 10. Conclusion and Next Work

The V0.4 experiment successfully demonstrated an isolated, stateful **default-deny inter-zone forwarding policy** in WSL2. The two intended TCP flows were reachable, while four representative unauthorized paths were blocked. A separate six-scenario automated regression run passed in full, and the final normal cleanup verification detected no failures among the specified resources.

This stage provides reproducible, evidence-backed network microsegmentation tests suitable for a technical portfolio. A subsequent iteration should expand negative-test coverage, add IPv6 and anti-spoofing considerations, evaluate failure handling and rollback, and introduce more detailed event logging and policy-change verification before making broader Zero Trust claims.
