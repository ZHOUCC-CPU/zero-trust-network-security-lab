## 1. Executive Summary

This project investigates whether a lightweight Linux
environment can support repeatable experiments in
network microsegmentation and least-privilege access
control.

A four-network-namespace topology was implemented
using virtual Ethernet links and a dedicated gateway
namespace. Stateful nftables rules enforced a
default-deny forwarding policy with two explicitly
permitted service paths.

Experiments from V0.3 through V0.9 covered topology
deployment, functional access control, automated
regression, baseline comparisons, bounded performance
measurements, firewall auditing, and reproducibility.

In the V0.6 controlled comparison, 36 of 36 scenario
executions matched their condition-specific
expectations. Under segmentation, all 12 expected
unauthorized access attempts were denied and all
six authorized attempts succeeded.

Later V0.8 and V0.9 experiments each recorded 18 of
18 successful scenario executions, with different
counter-audit evidence granularity.

These observations support the effectiveness of the
tested microsegmentation policy in the controlled
WSL2 laboratory. They do not demonstrate a complete
production Zero Trust Architecture.

## 2. Research Questions

The original research proposal defined four questions.

**RQ1. Can a resource-constrained Linux environment
support repeatable namespace-based segmentation?**

The WSL2 environment supported the demonstrated
topology, veth connectivity, routing, firewall policy,
repeatable tests, and normal cleanup.

This conclusion is bounded by the observed WSL2
runtime and retained experimental sessions.

**RQ2. Can least-privilege default-deny forwarding
permit approved flows while blocking other flows?**

Within the defined six-scenario test matrix, the
segmented condition produced 6/6 expected allows
and 12/12 expected denials in V0.6.

V0.8 additionally captured counter snapshots around
individual scenarios.

**RQ3. What are the operational and performance
costs of the experimental design?**

V0.7 recorded TCP connection timing, controlled
throughput, WSL-wide resource observations, and
individual deployment and cleanup durations.

These measurements are descriptive rather than
statistically generalizable overhead estimates.

**RQ4. How does WSL2 compare with an Ubuntu Server VM?**

The initial proposal considered both environments.
A complete equivalent VM-versus-WSL2 experiment is
not present in the validated research evidence.

This research question therefore remains partially
unanswered. No comparative VM performance or
security conclusions are claimed.

## 3. Experimental Runtime and Design Decision

The implemented environment consists of:

- Windows 11 as the host operating system.
- WSL2 with Ubuntu 24.04.
- Linux network namespaces and veth interfaces.
- The Linux routing stack and nftables.
- Bash and Python validation scripts.

The original V0.2 runtime record described a WSL2
configuration with a 3 GB memory limit and four
allocated CPUs.

WSL2 was used as a lightweight experimental runtime
under the available hardware constraints.

This decision does not establish that WSL2 is
universally more secure or performant than a
dedicated Ubuntu Server virtual machine.

The V0.2 feasibility record was originally supplied
from terminal observations. Later versions retained
additional real experimental evidence.

## 4. Network Architecture

Four project-owned network namespaces model a small
three-zone network and its policy gateway:

- `employee-ns`: simulated employee/client zone.
- `app-ns`: simulated application service zone.
- `data-ns`: simulated sensitive-data zone.
- `zt-gw-ns`: routing and policy enforcement.

The namespaces are joined by three veth pairs using
isolated internal IPv4 links.

The gateway is the intended forwarding point
between the three modeled zones.

This is a synthetic research topology, not an
enterprise deployment or a set of four virtual
machines.

The laboratory does not intentionally configure
external routes, NAT, or host-wide firewall policy.

During deployment, project-owned veth endpoints
are temporarily created in the default Linux
network namespace before being relocated.
Therefore, it would be inaccurate to claim that
deployment involves no host namespace interaction.

## 5. Security Policy and Threat Model

The V0.4 gateway policy uses stateful forwarding,
default-deny behavior, and explicit service
allow rules.

Two new-connection paths are authorized:

| Source | Destination | Protocol | Decision |
|---|---|---|---|
| Employee | Application | TCP 8080 | ALLOW |
| Application | Data | TCP 5432 | ALLOW |

Four representative unauthorized paths are tested:

| Source | Destination | Protocol | Decision |
|---|---|---|---|
| Employee | Data | ICMP | DENY |
| Employee | Data | TCP 5432 | DENY |
| Employee | Application | TCP 8081 | DENY |
| Data | Application | TCP 8080 | DENY |

Established and related return traffic is handled
by the connection-tracking policy.

Tests use temporary network endpoints. The TCP 5432
test endpoint is not a PostgreSQL database.

The primary assessed threats include unauthorized
cross-zone reachability and overly permissive
gateway forwarding.

Workload identity, user authentication, device
health, and continuous trust evaluation are outside
the implemented controls.

## 6. Experimental Methodology

The experiments progressed through seven documented
implementation and verification versions:

| Version | Main method |
|---|---|
| V0.3 | Topology and normal cleanup validation |
| V0.4 | Manual and automated policy testing |
| V0.5 | Three-round behavioral regression |
| V0.6 | Baseline-versus-segmented comparison |
| V0.7 | Bounded performance and resource sampling |
| V0.8 | Per-scenario firewall counter audit |
| V0.9 | End-to-end verification and normal cleanup |

Access-control tests distinguish an expected
connection success from an expected denial.

Where available, nftables rule counters provide
additional evidence of policy enforcement.

Experimental conditions and the depth of evidence
differ between versions. The result totals must
not be treated as one combined statistical sample.

Detailed methods and artifacts are linked from
the [Research Evidence Index](V1.0_RESEARCH_EVIDENCE_INDEX.md).

## 7. Controlled Security Comparison

V0.6 examined two conditions across three rounds:

1. A deliberately permissive routing baseline.
2. A segmented default-deny firewall condition.

Each condition executed the same six representative
scenarios in three rounds.

| Observation | Baseline | Segmented |
|---|---|---|
| Approved-flow successes | 6/6 | 6/6 |
| Reachable disallowed flows | 12/12 | 0/12 |
| Expected denials enforced | Not the baseline objective | 12/12 |
| Condition-specific outcomes | 18/18 | 18/18 |

Across both conditions, 36/36 executions matched
their respective expected outcomes.

Under segmentation, the observed counts were:

- False allows: 0/12.
- False denies: 0/6.
- Operational failures: 0 in completed rounds.

The baseline was intentionally permissive.
Its unauthorized-flow reachability was an expected
control observation, not a failed baseline test.

These results demonstrate behavior in the tested
matrix only. They do not establish a real-world
attack-prevention rate.

Source: [V0.6 Experiment Report](V0.6_EXPERIMENT_REPORT.md).

## 8. Performance and Operational Observations

V0.7 compared bounded TCP timing and throughput
measurements for the two approved service paths.

| Flow | Baseline median TCP connect | Segmented median TCP connect | Difference |
|---|---:|---:|---:|
| Employee to Application | 0.40397 ms | 0.41528 ms | +0.01131 ms |
| Application to Data | 0.38466 ms | 0.41259 ms | +0.02793 ms |

Receiver throughput in the selected measurement
conditions was approximately 50.115 Mbit/s.

Single measured deployment and cleanup durations
were 0.64535 s and 0.25646 s respectively.

Measurement order was not randomized.
CPU and memory samples covered the WSL guest
rather than isolating nftables overhead.

Consequently, the observed timing differences
must not be interpreted as statistically proven
firewall overhead or production capacity limits.

Source: [V0.7 Experiment Report](V0.7_EXPERIMENT_REPORT.md).

## 9. Firewall Audit and Repeatability

### V0.8 — Per-scenario audit

V0.8 completed 18/18 traffic scenarios across
three rounds.

The audit retained individual before-and-after
nftables counter snapshots, behavioral records,
and structured evidence for each scenario.

Counter observations support the test results,
but shared rule counters alone are not unique
flow attribution records.

Source: [V0.8 Experiment Report](V0.8_EXPERIMENT_REPORT.md).

### V0.9 — End-to-end validation

V0.9 completed 18/18 scenarios across three
rounds and verified three round-level firewall
counter comparisons.

It also recorded successful normal cleanup
and post-cleanup resource integrity checks.

The 15 primary evidence files passed SHA-256
consistency verification.

Unlike V0.8, V0.9 compares counters at the
round level rather than separately around
each individual access scenario.

Source: [V0.9 Experiment Report](V0.9_EXPERIMENT_REPORT.md).

## 10. Reproducibility and Safety

The project retains source scripts, test plans,
experiment reports, evidence records, and an
independent research evidence index.

Privileged execution uses reviewed scripts in
a root-controlled Linux staging directory rather
than executing mutable scripts directly from the
Windows-mounted repository.

Project state and namespace identity checks
protect the normal cleanup process against
deleting resources with mismatched identities.

Normal cleanup was observed to succeed.
Successful normal cleanup does not establish
recovery from every interruption or partial
failure.

SHA-256 comparisons support internal evidence
consistency; they are not independent
tamper-proof authentication.

## 11. Research Limitations

The principal limitations are:

1. Only six representative access scenarios
   were repeated in the main security matrix.
2. Testing used a single WSL2 environment.
3. The VM comparison question remains unresolved.
4. The policy mainly covers IPv4 forwarding
   through one isolated gateway namespace.
5. IPv6, spoofing, local-input traffic and
   other bypass conditions were not comprehensively
   evaluated.
6. Identity and device-posture verification were
   not implemented.
7. Service endpoints were temporary test servers,
   not production applications or databases.
8. Performance observations had limited
   repetitions and non-randomized ordering.
9. Abnormal failure recovery was not established
   through comprehensive live fault injection.
10. Local evidence hashes do not provide
    independently authenticated provenance.

These limitations restrict the conclusions to
the tested laboratory conditions.

## 12. Conclusions

The experiments demonstrate that WSL2 Ubuntu,
Linux network namespaces, veth interfaces, and
stateful nftables can support a repeatable
microsegmentation research prototype.

The V0.6 controlled comparison provides direct
evidence that the specified default-deny policy
blocked the tested unauthorized paths while
preserving both approved service paths.

V0.7 supplies bounded operational measurements,
while V0.8 and V0.9 add audit and reproducibility
evidence.

The project therefore supports claims about
tested network segmentation and controlled
verification, not complete Zero Trust Architecture
implementation, production readiness, or
cross-runtime equivalence.
