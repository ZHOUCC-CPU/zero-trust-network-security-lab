## 1. Objective and scope

Evaluate whether the existing Linux microsegmentation
prototype can be deployed, configured, exercised,
audited and cleaned up in a controlled WSL2 environment.

This is a network segmentation experiment inspired by
Zero Trust principles. It is not a complete Zero Trust
Architecture or a production security certification.

## 2. Experimental method

The trial used four Linux network namespaces:
`employee-ns`, `app-ns`, `data-ns`, and `zt-gw-ns`.

The reviewed V0.3 topology scripts deployed the
isolated environment. The V0.4 nftables policy
enforced default-deny IPv4 forwarding with two
explicitly authorized new-connection paths.

The runner executed the six-scenario V0.4
behavioral regression three times within the
same deployment.

Temporary HTTP servers were used for connectivity
testing. Port 5432 was a test endpoint, not a real
PostgreSQL database service.

Each round retained:

- The behavioral regression log.
- An nftables JSON snapshot before testing.
- An nftables JSON snapshot after testing.
- A calculated rule counter delta.

After the three rounds, guarded topology cleanup
was performed and a separate resource integrity
check inspected expected project resources.

## 7. Security and methodological limitations

- Tests cover six representative IPv4 scenarios.
- Identity authentication, device posture, and
  continuous authorization are not implemented.
- The gateway forwarding policy does not cover
  every host, IPv6, spoofing or local-input scenario.
- Topology deployment temporarily creates project
  veth interfaces in the default network namespace.
- Network behavior was observed in one WSL2 environment.
- The trial reused one topology across three rounds.
- Round-level counters are not per-scenario counters.
- The offline negative tests are simulated,
  not live destructive fault-injection experiments.
- This report is not evidence of production readiness.
